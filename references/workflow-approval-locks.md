# 十二步独立批准锁

## 执行规则

`workflow_run.py run/resume` 强制每步技术检查完成后停在 `waiting_approval`，一次调用最多新完成一步。只有独立复核者对当前步骤签发有效 Ed25519 批准，下一次 resume 才能进入下一步。第12步也必须签名，未签不能报十二步 completed。旧项目和旧计划没有免锁通道，不接受 `approved=true` 或自写观察者名称代替签名。

本功能不自动生成私钥、不替用户签名、不为旧项目补填同意，也不启动视频后端。

| 步骤 | 待用户批准的内容 | 未获批准时 |
|---|---|---|
| 1 歌词与时间轴 | 原曲、歌词、ASR来源、逐行边界及间奏 | 不进入第2步 |
| 2 全片方向 | 音乐结构、情绪、视觉方向、画幅及风格 | 不进入第3步 |
| 3 人物与参考 | 原图、人物身份/服装职责、来源与使用范围 | 不进入第4步 |
| 4 故事与剧组 | 故事节拍、组织结构、连续性、导演及八部门执行 | 不进入第5步 |
| 5 提示词与预演 | 当前编译、执行回执、全曲带音乐预演 | 不进入第6步 |
| 6 时间与口型计划 | 音乐窗口、演唱分配、镜头衔接与当前门禁 | 不进入第7步 |
| 7 静帧与代表样片 | 必需静帧、真实样片、动态观察与来源 | 不进入第8步，不扩批 |
| 8 批量产物 | 真实作业、媒体、逐章状态、费用与未解决项 | 不进入第9步 |
| 9 返修闭环 | 失败原因、冻结计划、替代素材、当前重审与汇总 | 不进入第10步 |
| 10 剪辑与全片 | 当前选段、全片候选、有声复核及最终合成依据 | 不进入第11步 |
| 11 交付包 | 最终媒体、来源、费用、对齐及必要独立口型证据 | 不进入第12步 |
| 12 复盘与版本 | 问题、修改、剩余限制、实际测试与发布证据 | 不声明十二步已完成 |

这些批准是每步收尾的额外放行条件，不替代原有风格、结构、静帧、预演、逐章、全片、口型及交付审核，也不等于批准任意额外支出或外部调用。

计划命令也按步骤约束：`workflow_execution.py` 在第1步只能run gate1，第5步只能run gate5/crew_pipeline/crew_rehearsal，第6步只能run gate6；禁止把run-required塞进早期步骤以一次运行后续门禁。草稿采纳timing只在第1步，design只在第4步，不能以第2步名义提前采纳故事设计。

## 防伪前提：必须分离执行与批准权限

1. **私钥只能在用户或独立复核者的环境中持有，执行 Agent 无法访问。** 不把私钥放在项目、工作区、共享临时目录、聊天附件或 Agent 可读账号内。
2. 宿主启动者提供外部公钥信任目录 `MV_REVIEW_TRUST_STORE`，并在受保护启动环境固定其文件 SHA-256：`MV_WORKFLOW_TRUST_STORE_SHA256`。目录不能放在待批准的项目内，摘要必须与文件匹配。
3. 信任目录中的批准者须有 `workflow_step` 用途授权，且未撤销；项目或待签请求携带的公钥不受信任。缺目录、缺固定摘要、签名错误或用途不符，一律不放行。
4. **代码、启动环境、信任目录和执行入口也必须由宿主权限保护。** 普通环境变量只是配置，不是操作系统身份认证；若 Agent 能改环境、信任目录、代码、换解释器或在仓库外直接调用工具，单靠本库不能实现全局防绕过。
5. 当前逐步锁的强制范围是 `workflow_run.py` 十二步编排器。独立脚本、Python API、MCP/供应商及手工改写文件不自动成为受控入口。要防恶意绕行，部署方须只允许 Agent 使用受保护编排入口，并限制其他写入/执行/网络权限。**本次未部署此类操作系统或宿主策略，不将编排锁宣传成全局权限沙箱。**

此处“外部”应当是执行权限之外，而不只是把文件挪到另一个同权限可写文件夹。信任目录、代码保护与批准者真实性须由部署方完成。不要让 Agent 自行生成一个新身份并注册成“用户”。

## 外部批准者配置

安装 `requirements-validation.txt` 所需依赖。由用户/部署者在受保护位置维护信任目录：

```json
{"reviewers":{"user-approval-key":{"public_key":"Ed25519原始32字节公钥的Base64","purposes":["workflow_step"],"revoked":false}}}
```

由启动者设置环境（示例路径需要替换）：

```powershell
$env:MV_REVIEW_TRUST_STORE = 'X:\受保护配置\workflow-reviewers.json'
$env:MV_WORKFLOW_TRUST_STORE_SHA256 = 'sha256:启动者核对后的目录文件SHA256'
```

固定摘要由用户核对后配置，不由项目文件或 Agent 当前选择的目录反算后自动接受。轮换信任目录须由启动者更新固定值，撤销/用途检查仍对每次批准生效。

## 每一步如何放行

### 1. 执行当前一步

```powershell
python scripts/workflow_run.py run PROJECT --plan PLAN.json
# 后续从同一计划恢复：
python scripts/workflow_run.py resume PROJECT --plan PLAN.json
```

材料不足仍等待原有审核；技术通过后 `status=waiting_approval`、`waiting_step=N`。此时进程非零退出以表示仍未完成，不是可以自动忽略的成功结果。重复 resume 不会进入 N+1，也不会为了等待批准重跑已经通过的 N。

### 2. 导出待审请求

```powershell
python scripts/workflow_approval.py request PROJECT --plan PLAN.json --step N --output REQUEST-N.json
```

只能导出当前顺序中等待批准的有效步骤。请求绑定项目绝对路径、计划 SHA、步骤号、此次 run_id、全部执行记录及前序批准摘要，包含可审阅的输入、输出、代码和进程证据。默认 `decision=pending`，不构成批准；导出不执行步骤，也不改变正式状态。

### 3. 用户独立检查并签名

用户在独立环境检查请求及其对应的真实产物。不能只看 Agent 的“已完成”概述。实际同意后只填写：

```json
{"decision":"approve","observer":"实际复核者","evidence":"本次实际核查内容、时间码或证据及允许的下一步"}
```

以上仅示意要填的字段，必须保留请求原有其他字段，不能只签这三个字段。在**私钥不可被 Agent 访问的环境**中使用受信任签名工具；若使用本库 CLI：

```powershell
python scripts/signed_evidence.py sign REQUEST-N.json --private-key PRIVATE_KEY.pem --key-id user-approval-key --output SIGNED-N.json
```

将签名证书交回项目固定位置（N须写为两位数，例如01）：

```text
PROJECT/state/workflow_approvals/step01.json
...
PROJECT/state/workflow_approvals/step12.json
```

文件中的签名不是私钥，可以交回。工具不从聊天语句自动推导并签署“用户同意”。没有明确批准就停止并汇报待审项。

### 4. 恢复下一步 / 查看状态

```powershell
python scripts/workflow_run.py resume PROJECT --plan PLAN.json
python scripts/workflow_run.py check PROJECT --plan PLAN.json
```

恢复先重新核对当前执行记录和全部前序批准链，再做下一步。check只读，不补执行、不补批准；全部12份当前有效批准通过后才报告 completed。

## 变更、失效与迁移

- 执行输入、产出或脚本版本改变，使旧执行记录失效；重做后新 run_id 要求新签名，不接受旧签名重放。
- 计划改变时旧运行不再匹配；从新计划重新建立执行和批准，不追认旧同意。
- 执行记录、日志、步骤号或已签上下文被改写，签名对不上，停在当前批准锁。
- 后续步骤显式声明接管共享输出时仍沿用原编排的“最后完成写入者”规则，不把正常的关5分镜更新误判为第4步首次输出被篡改；签名始终保留当时的执行快照，下一步须先获得此次接管步骤的批准。
- 前序证书被撤销、替换或重新签发，其摘要链改变，后续签名须重新核验并按当前链重新批准。
- 第12步签名前状态也只是 waiting_approval。旧无签名 completed 记录不再足以证明十二步完成。
- 中断/失败且可能写过产物的命令进入 `recovery_required`，保持原run_id、输入、代码、进程与active_command，不通过重新拍摄当前快照将旧产物变成“完成”。共享输出已被改写时，也不自动截断后续证据或重派早期步骤。须由独立执行者核对实际在途任务、媒体和日志后决定恢复方案；当前没有自动恢复许可或忽略未知结果的开关。
- 硬终止可能遗留 `.workflow-run.lock`。程序拒绝抢锁；部署方须先核实原进程及子进程已结束、没有写者，备份记录后手动处理遗留锁。删除锁不解除recovery_required，也不授予任何步骤批准。

## 不要把签名当作事实真伪裁判

签名只证明受信任持钥者批准了这些具体版本和记录。若虚构执行记录被复核者误签，签名无法自动识破；仍须查看实际产物和证据。签名不证明实际观看、电影感、口型正确、用户接收或费用账单真实性。自动检查也不能取代逐步的真实判断。
